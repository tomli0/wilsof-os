# Wilsof OS — Hermes project instructions

Follow AGENTS.md, CONTRIBUTING.md and docs/artifact-maintenance.md.
These current lifecycle rules supersede historical report/branch-retention
instructions where they conflict; they do not weaken safety or acceptance gates.

Reuse the existing active integration branch. Clean verified disposable output
within the task, using exact manifests and native filesystem/process/backing guards.
Do not create report-only branches, duplicate statuses, uncontrolled caches or
unregistered images. Preserve source/WIP, recovery, signing and unresolved evidence.

Issue #16 is the sole current dashboard. End with one concise verified update:
what works, what is broken, release blockers, next technical action and owner needs.
Historical reports stay organized in their existing archive paths/Git history;
unchanged blockers do not require another report commit. Keep automation paused.
No cleanup result implies source merge, ISO acceptance, release or physical approval.

## Persistent Pyramid execution

Permanent objective: a stable, secure, maintainable and independently developed
Arch/Hyprland/Dux Wilsof OS. Omarchy is not a source, dependency or development
baseline. Do not copy, port, adapt or translate any Omarchy code, scripts or
configuration. Obtain shared components directly from their original upstreams
with traceable provenance and applicable licenses. Do not claim existing-source
independence without a provenance review; passing tests do not prove code origin.
Changes to an existing Omarchy installation and migration work are outside scope.
Older replacement goals are historical, not current instructions. The current
milestone is read from #16, subject to the owner's latest scope.

For each Wilsof session, follow docs/pyramid-development.md. Read the latest #16
and #60 context and run `python3 automation/pyramid.py status` and `next` before
planning. The single private checkpoint is automation/.pyramid/state.json;
its .prev is recovery only, not a second dashboard. Never initialize over it.
Reconcile RUNNING attempts before new work; preserve FAIL and exact input identity.
Execute the highest-ranked authorized task, verify, record its receipt, and continue
to the next executable task within the current owner's scope. Do not re-plan or
repeat completed investigation without a documented changed-input repair.

Use Product, QA and Infrastructure workstreams, with one accountable Hermes.
Existing build/QA locks and the host artifact catalog remain mandatory; this
checkpoint lock is metadata-only. No competing build/maintenance, extra permanent
roots, new scheduler/model routes or automatic sudo authorization. Owner gates
remain physical/protected data, privilege, production trust and material scope/cost.
When blocked, preserve the checkpoint and one consolidated owner handoff; do not
invent lower-priority infrastructure work. The permanent administrative runner is
a separate security-gated proposal, not authority supplied by this workflow.
